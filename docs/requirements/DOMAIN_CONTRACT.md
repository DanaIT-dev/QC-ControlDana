# Доменный контракт: Реестр дефектных актов СГР

## Отличие Act и DefectItem

`Act` — официальный документ дефектного акта формы С-1 или С-23. Он принадлежит одному объекту недвижимости и одной организации-заказчику, имеет неизменяемый официальный номер и статус всего документа.

`DefectItem` — отдельная рабочая единица внутри акта: конкретный дефект в помещении. Один акт содержит несколько строк дефектов. Статус акта вычисляется из статусов его активных строк, а не задаётся независимо.

## Act

Поля:

- `id`
- `officialNumber` — отображаемый номер вида `С-1-2026-000001`
- `formCode` — внутренний код `S1` или `S23`
- `year`, `sequence` — ключ последовательности
- `objectId`
- `customerOrganizationId`
- `signedDocumentRef` — ссылка или идентификатор подписанного документа, пока nullable
- `status` — `IN_PROGRESS`, `COMPLETED` или `CANCELLED`
- `version` — optimistic concurrency
- `createdAt`, `updatedAt` — серверные метки времени (`timestamptz`)
- `cancelledAt`, `cancellationReason`, `cancelledByUserId` — аннулирование вместо физического удаления

## DefectItem

Поля:

- `id`, `actId`
- `location` — помещение или место
- `defectTypeId`
- `status` — `IN_PROGRESS` или `COMPLETED`
- `claimDetails`
- `plannedDeadline`, `claimDeadline`, `readyAt`, `thirdPartyDeadline`
- `notes`
- `createdAt`, `updatedAt`, `version`

Правила:

- новый `DefectItem` создаётся со статусом `IN_PROGRESS`;
- строку нельзя корректно завершить без `readyAt`;
- при переводе в `COMPLETED` сервер по умолчанию заполняет `readyAt`, если значение не передано явно;
- даты хранятся однозначно в UTC (`timestamptz`); серверные timestamps авторитетны.

## Статус Act

- учитываются только активные строки дефектов;
- если хотя бы одна активная строка `IN_PROGRESS`, акт = `IN_PROGRESS`;
- акт = `COMPLETED` только когда все активные строки `COMPLETED`;
- акт без строк считается `IN_PROGRESS`;
- статус `CANCELLED` устанавливается только процедурой аннулирования и не вычисляется из строк.

## Номер акта

Стратегия: отдельная таблица последовательностей `act_number_sequences` с ключом `(formCode, year)` и атомарным `INSERT ... ON CONFLICT DO UPDATE`.

- форматы: `С-1-2026-000001`, `С-23-2026-000001`;
- внутренняя кодировка формы латинская (`S1` / `S23`), официальный номер кириллический;
- последовательность своя для каждой пары форма + календарный год (UTC);
- номер уникален;
- одновременное создание двух актов не выдаёт один номер;
- номер не редактируется после создания (доменное правило и триггер БД);
- логика выполняется транзакционно на сервере;
- `COUNT(*) + 1` не используется.

## Архивирование

- `Act` физически не удаляется. Ошибочный акт аннулируется с причиной, временем и пользователем.
- `User` архивируется (`ARCHIVED` + `archivedAt`). Исторические назначения на объекты и дефекты сохраняются. Архивный пользователь не входит в систему, получает ту же ошибку, что и при неверном пароле, и теряет все активные сессии.
- Организация с непустым УНП не удаляется физически, если используется в актах (`ON DELETE RESTRICT`).
- Назначения инженера на объект фиксируют `assignedAt` и `unassignedAt`; история не уничтожается.

## Proposal

`Proposal` — коммерческое предложение альтернативного подрядчика по слоту `A`, `B` или `C` для одного `DefectItem`.

- `amount` — сумма предложения, не фактические затраты;
- валюта по умолчанию `BYN`;
- уникальность `(defectItemId, slot)`.

На этом этапе предложение не является подтверждённым расходом.

## Пользователи, объекты, организации

Роли пользователя: `ADMIN`, `SGR_MANAGER`, `RESPONSIBLE_ENGINEER`, `CONTRACTOR_ENGINEER`.

Объект недвижимости связан с ответственными инженерами many-to-many с историей назначений.

Организация может иметь роли `CUSTOMER`, `LIABLE_CONTRACTOR`, `ALTERNATIVE_CONTRACTOR` и несколько `WorkType`.

УНП:

- нормализуется удалением пробелов;
- пустое значение хранится как `NULL` и не конфликтует с другими пустыми;
- одинаковый непустой нормализованный УНП блокируется уникальным ограничением.

`DefectItem` связан many-to-many с ответственными инженерами и виновными организациями. Списки не сериализуются в одну строку через запятую.

## Прочие сущности этого этапа

- `DefectType` и `WorkType` — управляемые справочники.
- `Attachment` — только метаданные файла; загрузка не реализована.
- `AuditLog` — append-only журнал. Пользовательского CRUD удаления нет, каскадного уничтожения аудита нет.
- `SystemSettings.deadlineWarningDays` — по умолчанию 3.

## Принятые допущения

- Календарный год номера акта берётся из серверного UTC-времени создания.
- «Активный» DefectItem на этом этапе — любая строка, не связанная с аннулированным актом; отдельной отмены строки нет.
- Optimistic concurrency хранится в `version`, но конфликтные сценарии UI появятся позже.
- Демонстрационные персональные данные вымышлены.
