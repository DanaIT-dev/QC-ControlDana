# Матрица политик PostgreSQL RLS

Источник прикладных прав — сессия и `packages/domain/src/capabilities.ts`. RLS — второй уровень: deny-by-default, только verified transaction-local context.

Акты создаются вручную (`CREATE_ACT`). Интеграция с 1С исключена и не является каналом поступления данных.

Роли БД: `sgr_owner` (NOLOGIN, владелец объектов, BYPASSRLS только для owner/migrator), `sgr_app`, `sgr_auth`, `sgr_worker` (NOSUPERUSER, NOBYPASSRLS). Runtime-роли не владеют таблицами и не могут `SET ROLE sgr_owner`.

Verified context: HMAC-SHA256 (`RLS_CONTEXT_SECRET`), `SECURITY DEFINER` `sgr_set_request_context`. Политики не доверяют голому `set_config` userId/role.

Легенда прав: `S` SELECT, `I` INSERT, `U` UPDATE, `D` DELETE. Пусто — нет GRANT. `—` не применимо.

## Политики по ролям приложения

### SUPER_ADMIN

Не входит в `sgr_is_staff()` и `sgr_is_admin()`. `sgr_is_business_user()` ложен. SELECT бизнес-таблиц через `OR sgr_is_super_admin()` при verified HMAC-контексте. Прямые INSERT/UPDATE/DELETE бизнес-таблиц запрещены. Исключения — SECURITY DEFINER: `sgr_create_pending_user`, `sgr_grant_admin`, `sgr_revoke_admin`. Каталог сотрудников для назначения ADMIN — `sgr_super_admin_directory` (включая `PENDING_ROLE` и `CONTRACTOR_ENGINEER`). Диагностика активных SUPER_ADMIN — `sgr_active_super_admins()` (только owner/migrator, без `passwordHash`). AuditLog доступен на чтение и неизменяем. Назначение ADMIN блокирует строку и не снимает последнего активного ADMIN. Снятие ADMIN восстанавливает рабочую роль или `PENDING_ROLE`, если прежняя роль была `UNASSIGNED`.

### ADMIN

Все бизнес-строки в пределах GRANT `sgr_app` и verified context. Capabilities по-прежнему режет API (`403` без права). RLS не расширяет права сверх матрицы capabilities (нет GRANT на лишнее).

### SGR_MANAGER

Все бизнес-строки актов/дефектов/предложений/вложений/истории. Нет `users` мутаций, нет `system_settings` UPDATE, нет `VIEW_SYSTEM_STATUS` (outbox/email/sla_evaluation SELECT закрыт).

### RESPONSIBLE_ENGINEER

Граница актов/дефектов — активные `property_object_engineers` (`unassignedAt IS NULL`). Каталог `property_objects` / `organizations` — SELECT всех строк (`VIEW_REFERENCE_DATA`). Все акты и все дефекты закреплённых объектов. `DefectItemEngineer` не даёт доступ к чужому объекту. Proposal A — только SELECT. Proposal B/C — ни SELECT, ни I/U/D. История — assigned object, без B/C. Снятие с объекта закрывает EXISTS немедленно; повторное назначение — та же unique `(propertyObjectId, userId)`.

### CONTRACTOR_ENGINEER

SELECT актов, дефектов, объектов, вложений и THIRD_PARTY SLA только через активную `user_organization_memberships` и `defect_item_liable_organizations` (`sgr_contractor_can_see_*`). Роль сама по себе строки не открывает. Membership пишет только `ADMIN`/`MANAGER`; подрядчик читает свои строки и не меняет их. История: нет SELECT `audit_logs`. Чат акта недоступен. Уведомления `ACT_CHAT_MENTION` не читаются.

## Контекст и изоляция пула

1. Interactive Prisma transaction.
2. Первая операция: `SELECT sgr_set_request_context($token)`.
3. Callback только с transaction client.
4. `SET LOCAL` / GUC сбрасываются при COMMIT/ROLLBACK.
5. Поддельная, изменённая и просроченная подпись → ошибка без утечки secret.
6. Worker: отдельный `sgr_set_worker_context`, GRANT только `sgr_worker`.

## Rollback

`prisma migrate` не откатывает RLS автоматически. Recovery: новая forward-миграция или restore из backup. Запрещено включать SUPERUSER/BYPASSRLS в runtime URL. Rotation `RLS_CONTEXT_SECRET`: новая строка в `sgr_rls_secrets`, overlap, затем `revoked_at` на старой.
